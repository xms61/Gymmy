# Testing

There is no automated test suite yet. Tests will use Node's built-in runner (`node:test` with `node:assert/strict`) on TypeScript files, with no test framework dependency.

| Command | What | Where |
| :-- | :-- | :-- |
| _none yet_ | Unit and integration tests | `tests/**/*.test.ts` |

Coverage thresholds, once coverage runs: lines and functions ≥ 85 %, branches ≥ 75 %.

Until the suite exists, check a change by running `npx tsc -b`, `npm run build`, and the app itself with `npm run dev`.

## Isolation
- Tests never touch the network or the real data directory.
  - Server tests open their database in a fresh temp folder (`fs.mkdtempSync(path.join(os.tmpdir(), 'gymmy-'))`), never `data/`.
  - Server routes are tested by calling the request handler directly, not over a socket.
  - Logic that uses `fetch` or `localStorage` is tested through pure functions that take plain data in and return data out.
- Every test builds its own fixtures with a small function (`emptyStore()`, `catalogWithTenTracks()`). No state carries over from one test to the next.
- Use in-memory or temp-dir databases, never the app's singleton for writes.
- Fixture data is generated by code, never committed as binary files.

## Writing tests
- One test per behavior, named after the behavior: `rejects a live recording`, not `test 3`.
- Put rule corpora in a table and loop over it: `const CASES: [input: string, expected: boolean][] = [...]`.
- Use equality assertions (`assert.equal`, `deepEqual`), so a failure shows both values.
- Test behavior through public functions. Don't assert on private helpers, the size of constant lists, or `typeof x === 'function'`.
- A bug fix adds the test that would have caught it.
- Delete tests that only lock in data or implementation details.

## When a test fails
- Rerun the single file (see the one-file command in `AGENTS.md`) to see the full error.
- Fix the code, not the assertion, unless the assertion was wrong. Say which one it was in the PR.
